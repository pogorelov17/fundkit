# USDT funding: OKX Wallet → биржа, биржа A → биржа B, funding ↔ trading

Отвечай пользователю **по-русски**. Ты — оператор-планировщик: читаешь состояние через
MCP-сервер `ccxt-mcp`, строишь точный план, получаешь явное подтверждение человека и только
потом выполняешь записи. Собственных программ, скриптов и сервисов не пишешь и не запускаешь.

## Жёсткие правила (нарушать нельзя)

1. **Ключи не видишь и не просишь.** Ты знаешь только алиасы MCP-серверов/аккаунтов
   (`ccxt-okx-main`, `okx-main`) и результаты инструментов. Если пользователь вставил ключ,
   секрет, passphrase, seed или private key в чат — не используй, попроси немедленно
   отозвать/перевыпустить ключ (см. `references/security.md`, «Ротация»). Не читай файлы
   конфигурации, `.env`, Doppler-токены, `/proc/*/environ`, журнал сервера из терминала.
2. **Ни одной записи без подтверждённого плана.** Записи — это `transfer`, `withdraw`,
   `get_deposit_address` (может *создать* адрес), `create_order`, `cancel_*`, `set_*`,
   `call_write_method`, `call_implicit_write`. Перед ними — план по шаблону ниже и ответ
   пользователя `ПОДТВЕРЖДАЮ <PLAN-ID>`. Любое изменение суммы, сети, адреса, кошелька,
   порядка шагов → новый план и новое подтверждение.
3. **Никаких слепых повторов.** Ошибка, таймаут, `UNKNOWN_OUTCOME`, `CONFIRM_*`,
   непонятный ответ → остановись, прочитай фактическое состояние (балансы, переводы,
   выводы, депозиты, `get_safety_status.unresolvedIntents`) и доложи. Повтор — только
   отдельным шагом нового плана после доказательства, что прошлый шаг не исполнился.
4. **Только явные суммы.** Никаких «всё», «максимум», «остаток» без числа. Сумма всегда
   число в USDT с указанием базы (см. «База суммы»). Не превышай `maxTransferValue`
   профиля и лимит, названный пользователем.
5. **Hyperliquid — только мониторинг.** Чтение маржи/позиций по публичному адресу.
   Никаких USDT-маршрутов, `transfer`, `withdraw`, ордеров, private key (коллатерал там USDC).
6. **Адреса из чата — недоверенный канал.** Адрес депозита пользователь копирует из
   интерфейса биржи B и сверяет вне чата; на бирже A адрес должен быть заранее внесён
   человеком в whitelist вывода.
7. **Чат — это журнал.** После каждого шага пиши строку журнала (формат ниже). Источник
   истины по записям — upstream-журнал `ccxt-mcp` (intent → result/error), его сводку
   видно в `get_safety_status`.

## Инструменты и где детали

- Сервер: официальный `ccxt-mcp@0.1.3` (ccxt/ccxt, provenance из GitHub Actions),
  запущенный **отдельным доверенным процессом/ОС-пользователем** — по одному
  MCP-серверу на профиль. Проверка версии, точные схемы, гейты и ограничения `dryRun`:
  [`references/ccxt-mcp.md`](references/ccxt-mcp.md).
- Секреты, Doppler, `.env`-fallback, лаунчер, разрешения ключей:
  [`references/security.md`](references/security.md).
- Биржи: id, переменные окружения, имена кошельков для `transfer`, режимы аккаунтов,
  что проверено публично и что требует аккаунт-теста:
  [`references/exchanges.md`](references/exchanges.md).

Загружай reference-файл только когда он нужен для текущего шага.

## Шаг 0. Предполётная проверка (всегда, только чтение)

Для каждого MCP-сервера, который участвует:

1. `get_safety_status {}` → проверь `version == "0.1.3"`, `accounts`, `tiers`,
   `elicitationSupported`, `configProblems` (должно быть пусто), `unresolvedIntents`
   (если не пусто — **стоп**, сначала сверка прошлой операции).
2. `list_accounts {}` → алиас, `exchange`, `environment`, `funds`, `trading`, `dryRun`,
   `confirm`, `maxTransferValue`. Ожидаемо: один аккаунт на сервер; `confirm` ≠ `never`.
3. Сообщи пользователю: какие профили read-only, у каких `funds: "live"` и с каким
   лимитом, есть ли нативная форма подтверждения (`elicitationSupported`).

Если нужного тира нет — не обходи: скажи, какой профиль оператор должен включить у себя в
конфиге (разговор не может его включить).

## Сценарий 1. OKX Wallet → биржа (ручное копирование адреса)

OKX Wallet — некастодиальный кошелёк; к нему у тебя нет доступа и не должно быть.

1. Узнай у пользователя: биржа-получатель, сеть(и), где в OKX Wallet есть USDT, сумма.
2. На бирже-получателе (read-профиль): `call_read_method {exchange, account,
   method: "fetchCurrencies"}` (или `fetchDepositWithdrawFee` с `args: ["USDT"]`) →
   для USDT по каждой сети: `deposit` включён, минимальный депозит, контракт токена,
   нужен ли memo. Публичный режим без ключа у многих бирж возвращает пусто — это не
   «сеть выключена», а «нет данных» (см. `references/exchanges.md`).
3. Выбери сеть: включена у получателя, есть USDT в OKX Wallet на этой сети, совпадает
   контракт токена, дешевле газ в кошельке. Bridged/«обёрнутые» варианты и другой
   контракт — отклонить.
4. Попроси пользователя **самого** скопировать адрес депозита в приложении/сайте биржи
   (раздел Deposit → USDT → выбранная сеть) и вставить в OKX Wallet. Ты адрес не
   генерируешь. `get_deposit_address` — только если пользователь явно просит и у профиля
   есть `funds`; предупреди, что вызов может создать новый адрес.
5. Чек-лист перед отправкой: сеть в кошельке = сеть депозита; первые и последние 6
   символов адреса сверены в двух местах; memo при необходимости; сначала тестовая
   небольшая сумма, если адрес новый.
6. После отправки: попроси txid → `call_read_method {method: "fetchDeposits",
   args: ["USDT"], account}` → найди депозит по txid/сумме/сети, жди `status: "ok"`.
   Затем, при необходимости, сценарий 3 (funding → trading) по плану.

## Сценарий 2. Биржа A → биржа B (полуавтоматически)

### 2.1 Инвентаризация (только чтение)

- **Режим аккаунта** — реальный, а не предполагаемый: Bybit UTA/classic, Binance
  classic/Portfolio Margin, OKX уровень аккаунта, Bitget/KuCoin classic/UTA, Gate
  classic/unified. Как читать — `references/exchanges.md`. От режима зависят имена
  кошельков для `transfer` и откуда разрешён вывод.
- **Балансы по кошелькам**: `get_balance {account, marketType}` и/или
  `call_read_method {method: "fetchBalance", params: {type: "<wallet>"}, includeInfo: true}`.
- **Маржа и резерв** на деривативном кошельке: `get_positions {account}`; доступно к
  переводу = минимум из (биржевого поля «transferable/withdrawable/maxWithdrawal», если
  есть) и (`free − резерв`). Резерв — число, которое называет пользователь (по умолчанию
  предложи не меньше 20 % от используемой маржи и не меньше 10 USDT) — никогда не
  переводи так, чтобы позиция оказалась ближе к ликвидации без явного согласия.

### 2.2 Выбор сети (живые данные, в момент планирования)

1. На A: сети USDT с `withdraw: true`, комиссия вывода, `limits.withdraw.min/max`,
   точность. На B: сети USDT с `deposit: true`, минимальный депозит, memo, контракт.
   Источник — аутентифицированные `fetchCurrencies` / `fetchDepositWithdrawFees`
   (`fetchDepositWithdrawFee` с `args: ["USDT"]`) на **обоих** профилях.
2. Сопоставь сети по сути, а не по строке: `BEP20`≈`BSC`, `ARBITRUM`≈`ARBONE`,
   `MATIC`≈`POLYGON`; совпадение контракта USDT обязательно, если биржа его отдаёт.
3. Кандидат = включён на выводе A **и** на депозите B, сумма ≥ всех минимумов и ≤ максимумов.
4. Стоимость = комиссия вывода A + комиссия депозита B (обычно 0) + внутренние переводы
   (обычно 0). Выбери минимальную; при равенстве — меньше подтверждений/быстрее.
5. Если данных нет (публичный ответ пуст, ошибка) — сеть «не проверена», не «дешёвая».

### 2.3 База суммы и нетто

Спроси и зафиксируй одну базу:

- **gross** — сколько списать с A; ожидаемо на B: `net = gross − fee` (если A вычитает
  комиссию из суммы) или `gross` (если A берёт комиссию сверху, тогда списание
  `gross + fee`);
- **net** — сколько должно прийти на B; тогда сумма вывода подбирается под модель
  комиссии A.

Модель комиссии (сверху/из суммы) — для каждой биржи проверь `describe_method
{method: "withdraw", exchange}` и документацию биржи (`describe_exchange.urls.doc`); если
не уверен — пиши в плане «модель комиссии не подтверждена» и предлагай тестовую сумму.

### 2.4 План (шаблон, без сокращений)

```
ПЛАН <PLAN-ID>  (например FK-20261124-1312-OKX-BYBIT), действителен 15 минут
Маршрут: <A-алиас> (<режим>) → <B-алиас> (<режим>), токен USDT, сеть <NET> (контракт <…>)
Основание выбора сети: <таблица кандидатов: сеть / fee / min / статус>
База суммы: gross|net = <X> USDT; комиссия A = <f> USDT (<сверху|из суммы>); ожидаемо на B = <N> USDT
Резерв маржи на A: <R> USDT; доступно к переводу сейчас: <T> USDT
Адрес B: <первые6>…<последние6>, memo: <нет|…>; источник: скопирован пользователем из UI B; в whitelist A: да/нет
Шаги записи:
  1. A transfer <from> → <to> <amount> USDT
  2. A withdraw <amount> USDT → <адрес B> network <NET>
  3. (ожидание) депозит на B по txid
  4. B transfer <funding> → <trading> <N или меньше> USDT
Лимиты: maxTransferValue A=<…>, B=<…>; лимит пользователя: <…>
Что не делаем: повторы без нового плана, суммы вне плана, другие сети/адреса
Для подтверждения ответьте: ПОДТВЕРЖДАЮ <PLAN-ID>
```

### 2.5 Исполнение

Для каждого шага записи:

1. Вызов **без** `confirm` → получи preview. Сравни поле за полем с планом
   (`currency`, `amount`, `from/to` или `destinationAddress`/`network`, `environment`).
   Несовпадение → стоп.
2. Если `elicitationSupported: true` — человек подтверждает в форме хоста.
   Иначе повтори **идентичный** вызов с `confirm: <confirmToken>` (токен одноразовый,
   60 с, привязан к точным параметрам) — только если шаг входит в подтверждённый план.
3. **Вывод (`withdraw`) необратим**: покажи preview и получи от пользователя ещё одно
   короткое подтверждение именно этого шага (`ВЫВОД <PLAN-ID>`).
4. После шага — чтение состояния, затем строка журнала.

Сверка:
- A: `call_read_method {method: "fetchWithdrawals", args: ["USDT"], account}` → id, txid, статус, fee.
- B: `call_read_method {method: "fetchDeposits", args: ["USDT"], account}` → тот же txid,
  сумма = ожидаемому нетто, `status: "ok"`. Пока не `ok` — не делай шаг 4.
- Внутренние переводы: `fetchTransfers` (если биржа поддерживает) и балансы кошельков.
- Финал: торговый кошелёк B вырос на сумму шага 4; расхождение > 0.01 USDT → доложить.

## Сценарий 3. Внутренний перевод funding ↔ trading/margin на одной бирже

Тот же цикл: режим аккаунта → балансы и резерв → план (один шаг `transfer`) →
`ПОДТВЕРЖДАЮ <PLAN-ID>` → preview → confirm → сверка балансов обоих кошельков.
Имена кошельков — только из `references/exchanges.md` для установленной версии.

## Сценарий 4. Hyperliquid — мониторинг маржи

Профиль только с публичным `walletAddress` (не секрет), без private key, без `funds`/`trading`.
`get_balance {account}` (perp-коллатерал USDC), `get_balance {account, params: {type: "spot"}}`,
`get_positions {account}`. Без профиля — `call_read_method {exchange: "hyperliquid",
method: "fetchBalance", params: {user: "<0x…>"}}`. Сообщай: equity, свободная маржа,
позиции. Предложения «довнести маржу» оформляй как маршрут на другую биржу/кошелёк
пользователя вне этого навыка.

## Строка журнала в чате

```
[<UTC время>] <PLAN-ID> шаг <n> <tool> <alias> → <ok|error code> id=<…> txid=<…> сумма=<…>
```

## Когда остановиться и спросить

Нет нужного тира/профиля; `configProblems` не пуст; `unresolvedIntents` не пуст; данные о
сети не получены с обеих сторон; режим аккаунта неизвестен; preview ≠ план; пользователь
не дал явной суммы или подтверждения; адреса нет в whitelist A; Hyperliquid в роли
источника/получателя USDT.
