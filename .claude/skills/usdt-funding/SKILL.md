# USDT funding: OKX Wallet → биржа, биржа A → биржа B, funding ↔ trading

Отвечай пользователю **по-русски**. Ты планируешь и исполняешь записи только через MCP-сервер
`ccxt-mcp`. Сначала читаешь состояние, затем строишь точный план. Записи выполняешь только
после явного согласия человека. Своих программ и скриптов не пишешь и не запускаешь.

## Жёсткие правила

1. **Ключей не видишь и не просишь.** Ты знаешь только алиасы (`okx-main`) и результаты
   инструментов. Если пользователь вставил в чат ключ, секрет, passphrase, seed или private key,
   не используй его и попроси сразу перевыпустить ключ. Не читай `.env`, конфиги, окружение
   процессов (`/proc/*/environ`) и журнал сервера через shell.
2. **План привязан к точным аргументам.** Записи — это `transfer`, `withdraw`,
   `get_deposit_address` (при первом вызове может *создать* адрес), `create_order`, `cancel_*`,
   `set_*`, `call_write_method`, `call_implicit_write`. Перед любой записью покажи план с
   **полным JSON аргументов** каждого вызова и получи ответ `ПОДТВЕРЖДАЮ <PLAN-ID>`. Если
   меняется хоть одно поле (сумма, сеть, адрес, memo, кошелёк, `params`, порядок), нужен новый
   план и новое подтверждение.
3. **Вывод подтверждается отдельно и заранее.** Перед **первым** вызовом `withdraw` покажи его
   точный JSON и получи от человека отдельное `ВЫВОД <PLAN-ID>`. На хостах с нативной формой
   (Claude Code и Codex её поддерживают) первый же вызов открывает форму, и принятие формы сразу
   отправляет вывод.
4. **`network` указывай только на верхнем уровне, `params` оставляй `{}`.** Не клади в `params`
   ключи сети, цепочки или комиссии (`chain`, `network`, `fee`, `includeFee` и т. п.): они уходят
   на биржу и могут переопределить проверенную сеть. При этом их не видно ни в preview, ни в
   нативной форме (проверено). Непустой `params` допустим, только если он целиком показан в
   плане и подтверждён.
5. **Повторять запрещено, пока исход неизвестен.** На `UNKNOWN_OUTCOME`, таймаут хоста, обрыв
   связи, отсутствие ответа или любую ошибку не из списка «до отправки» (раздел 2.6) ничего не
   повторяй: сверь состояние по истории операций. Повтор возможен только новым планом и
   только когда доказано, что операция не исполнилась.
6. **Суммы только явные.** Не принимай «всё», «максимум» или «остаток» без числа. Каждая сумма
   — число в USDT с указанием, что оно означает: списание, аргумент вызова или зачисление
   (см. 2.3). Не превышай `maxTransferValue` и лимит пользователя.
7. **Сеть, комиссию, минимум и контракт не угадывай.** Если поле не пришло в живом ответе, оно
   «неизвестно», а сеть с неизвестным полем не годится. Тестовые «пробные» переводы не предлагай.
8. **Hyperliquid — только мониторинг** по публичному адресу. Никаких переводов, выводов, ордеров
   и private key (коллатерал там USDC).
9. **Адресам из чата не доверяй.** Адрес депозита человек копирует из интерфейса биржи B и
   сверяет вне чата. Для вывода с биржи A адрес должен быть заранее внесён в whitelist A.

## Синтаксис вызовов

У `call_read_method` всегда два обязательных поля, `exchange` и `method`, даже если указан
`account`. Без `exchange` хост вернёт `-32602 Required at exchange`. Значение `exchange` должно
совпадать с биржей аккаунта. Позиционные аргументы передавай через `args`, например
`[code, since, limit]`, а пропуск обозначай `null`.

```text
call_read_method {"exchange":"okx","account":"okx-main","method":"fetchDepositWithdrawFee","args":["USDT"],"includeInfo":true}
call_read_method {"exchange":"okx","account":"okx-main","method":"fetchBalance","params":{"type":"funding"},"includeInfo":true}
call_read_method {"exchange":"okx","account":"okx-main","method":"fetchWithdrawals","args":["USDT",null,20]}
call_read_method {"exchange":"bybit","account":"bybit-main","method":"fetchDeposits","args":["USDT",null,20]}
```

`call_implicit_get` в закреплённой связке ccxt-mcp 0.1.3 + ccxt 4.5.94 не принимает ни один
raw-эндпоинт (`UNKNOWN_ENDPOINT`, проверено). Пользуйся только unified-методами с
`includeInfo: true`. Подробности: [`references/ccxt-mcp.md`](references/ccxt-mcp.md).

## Шаг 0. Предполётная проверка (только чтение)

Для каждого участвующего сервера:

1. Вызови `get_safety_status {}`. Должно быть `version: "0.1.3"` и `ccxtVersion: "4.5.93"`
   (так ccxt 4.5.94 сообщает свою версию), `configProblems` пуст. Запомни
   `elicitationSupported`. Если `unresolvedIntents` не пуст, **остановись**: журнал общий для
   всех профилей одного ОС-пользователя, поэтому там могут быть записи другого алиаса. Сначала
   сверь их через сервер с этим алиасом.
2. Вызови `list_accounts {}`: проверь алиас, `exchange`, `environment`, `funds`, `dryRun`,
   `confirm` (не `never`) и `maxTransferValue`. Алиасы должны быть уникальны на всех серверах.
3. Сообщи пользователю, какие профили только читают, у каких `funds: "live"` и с каким лимитом,
   есть ли нативная форма. Недостающий тир включает только оператор в конфиге, из разговора
   это невозможно.

## Сценарий 1. OKX Wallet → биржа (ручная отправка)

OKX Wallet — некастодиальный кошелёк. Отправляет из него только человек, вручную.

1. Узнай у пользователя биржу-получатель, сети, в которых в OKX Wallet есть USDT, и сумму.
2. Прочитай данные сети у получателя:
   `call_read_method {"exchange":"<B>","account":"<B-alias>","method":"fetchDepositWithdrawFee","args":["USDT"],"includeInfo":true}`.
   В `info` найди по сети: депозит включён, минимум депозита, контракт, memo. Пустой ответ или
   ошибка означают «нет данных», а не «сеть выключена» (раздел 2.2).
3. Сеть подходит, если депозит включён, контракт совпадает с USDT в кошельке и сумма не меньше
   минимума. Bridged-варианты и чужие контракты отклоняй.
4. Адрес по умолчанию человек **сам** копирует в приложении биржи (Deposit → USDT → сеть).
   `get_deposit_address` вызывай, только если человек отдельно попросил, у профиля есть
   `funds`, и человек ответил `АДРЕС <PLAN-ID>` на точный JSON вызова. Предупреди, что первый
   вызов может создать новый адрес и что `dryRun` этот инструмент не останавливает.
5. Перед отправкой человек проверяет: сеть в кошельке совпадает с сетью депозита, первые и
   последние 6 символов адреса сверены в двух местах, memo указан, если нужен.
6. После отправки попроси txid и найди депозит в
   `call_read_method {"exchange":"<B>","account":"<B-alias>","method":"fetchDeposits","args":["USDT",null,20]}`
   по txid, сумме и сети. Дождись `status: "ok"`. Если нужен перевод в торговый кошелёк,
   выполни сценарий 3.

## Сценарий 2. Биржа A → биржа B (полуавтоматически)

### 2.1 Режим аккаунта и доступная сумма (живые данные)

- **Режим аккаунта** определяй по живому ответу, не по догадке: Bybit UTA или classic, OKX
  `acctLv` (`fetchAccounts` с `includeInfo`), Binance classic или Portfolio Margin, Gate / Bitget
  / KuCoin classic или unified. От режима зависят имена кошельков и то, откуда разрешён вывод.
  Режим неизвестен — стоп.
- **Доступно к переводу или выводу** определяй по полю биржи для этого режима в raw-ответе
  `fetchBalance` нужного кошелька с `includeInfo: true`. В плане укажи имя поля и его значение.
  `free` без такого поля не считается доступной суммой. Если поля нет, стоп.
- **Резерв маржи** называет пользователь; предложи не меньше 20 % используемой маржи и не
  меньше 10 USDT. Позиции смотри через `get_positions`. Можно перевести
  `min(биржевое доступное, free − резерв)`. Перевод не должен приближать позицию к ликвидации без
  явного согласия.

### 2.2 Выбор сети (обе стороны, живые данные)

1. На **каждой** стороне вызови `fetchDepositWithdrawFee` с `args:["USDT"]` и `includeInfo:true`
   через аккаунт этой биржи. `fetchCurrencies` для выбора сети не используй: ответ больше 80 000
   символов целиком заменяется маркером `{"truncated":true}`. Так было даже без ключа у Bitget,
   WhiteBIT, KuCoin и Gate.
2. В unified-части есть только комиссии. Флаги включённости, минимумы, контракт, memo, точность
   и тип комиссии бывают только в `info`, и поля у каждой биржи свои (см.
   [`references/exchanges.md`](references/exchanges.md)). Если нужного поля нет, оно
   **неизвестно**, и сеть не годится. Ничего не выводи из названия сети.
3. Кандидат подходит, только если вывод на A включён (в том числе для API, если биржа это
   различает) **и** депозит на B включён, а сумма в пределах всех минимумов и максимумов.
   Контракт должен совпадать. Если какая-то сторона его не отдаёт, напиши в плане «контракт
   не подтверждён <биржей>», и человек сверяет его в интерфейсе.
4. Сопоставляй сети по контракту, а не по строке (`BEP20`≈`BSC`, `ARBITRUM`≈`ARBONE`,
   `MATIC`≈`POLYGON`).
5. Стоимость сети — сумма комиссии A, комиссии депозита B и внутренних переводов. Выбирай самую
   дешёвую; при равенстве — быструю.

### 2.3 Сколько списать, сколько отправить, сколько придёт

Держи три числа раздельно:

- `D` — **gross-списание** с A (сколько уйдёт с баланса);
- `W` — **аргумент `amount`** в `withdraw`;
- `C` — **net-зачисление** на B.

Пусть `f` — комиссия вывода A (фиксированная плюс процентная, если есть), `d` — комиссия
депозита B.

| Модель комиссии A | `D` | `C` |
|---|---|---|
| сверху | `W + f` | `W − d` |
| из суммы | `W` | `W − f − d` |
| **не подтверждена** (по умолчанию) | от `W` до `W + f` | от `W − f − d` до `W − d` |

Модель считай неподтверждённой, пока её прямо не показывают поля биржи или документация.
`describe_method` модель комиссии не показывает. Для неподтверждённой модели требуй, чтобы
доступно было не меньше `W + f`, а нижняя граница `C` была не меньше минимума депозита B.
Финальный перевод на B планируй не больше нижней границы `C`.

Пример: бюджет списания 100 USDT, комиссия 1 USDT берётся сверху, других комиссий нет. Тогда
`W = 99`, `D = 100`, `C = 99`. Если модель не подтверждена, то при `W = 99` выйдет
`D` от 99 до 100 и `C` от 98 до 99.

- **Валюта комиссии.** Если комиссия берётся не в USDT, укажи её валюту и проверь баланс этой
  валюты. Если валюта неизвестна, стоп.
- **Точность.** `W` сам округли **вниз** до точности сети. ccxt округляет по математическим
  правилам и может округлить вверх.
- **Минимумы.** Проверь `W` против минимума вывода A, а `C` — против минимума депозита B.

### 2.4 План

```
ПЛАН <PLAN-ID>  (например FK-20261124-1312-OKX-BYBIT), действителен 15 минут
Маршрут: <A-alias> (<режим>) → <B-alias> (<режим>), USDT, сеть <NET>, контракт <…>
Кандидаты: <сеть / вывод A / депозит B / fee / min / источник поля>
Доступно на A: <поле>=<значение>, резерв <R>, к переводу <T>
Суммы: D=<…>, W=<…>, C=<…> (модель комиссии: <сверху|из суммы|не подтверждена>), валюта fee <…>
Адрес B: <первые6>…<последние6>, memo <нет|…>, скопирован человеком из UI B, в whitelist A: да
Вызовы (точно эти аргументы):
  1. transfer {"account":"<A>","code":"USDT","amount":<…>,"fromAccount":"<…>","toAccount":"<…>","params":{}}
  2. withdraw {"account":"<A>","code":"USDT","amount":<W>,"address":"<…>","network":"<NET>","params":{}}   ← отдельное ВЫВОД <PLAN-ID>
  3. (ожидание) депозит на B по txid
  4. transfer {"account":"<B>","code":"USDT","amount":<≤ C_min>,"fromAccount":"<…>","toAccount":"<…>","params":{}}
Перепроверка перед каждой записью: доступно/резерв, сеть/комиссия/минимумы на обеих сторонах
Лимиты: maxTransferValue A=<…>, B=<…>; лимит пользователя <…>
Для подтверждения: ПОДТВЕРЖДАЮ <PLAN-ID>
```

### 2.5 Исполнение каждой записи

1. **Перепроверка.** Сразу перед вызовом заново прочитай доступную сумму и резерв, а также
   включённость сети, комиссию и минимумы на обеих сторонах. Изменилось что-то из плана —
   нужен новый план и новое подтверждение. Что-то стало неизвестно — стоп.
2. **Снимок истории.** Запомни последние ID в `fetchWithdrawals` / `fetchTransfers` /
   `fetchDeposits` и балансы затронутых кошельков. Это база для сверки.
3. **Вызов с аргументами ровно из плана.**
   - `elicitationSupported: true`: вызов открывает форму хоста. Человек сверяет текст формы с
     планом. Форма показывает только preview (сумма, кошельки или адрес и сеть, memo,
     окружение), а единственное поле в ней — `confirm` (да/нет); `params` в форме не видны.
     Принятие сразу отправляет запись.
   - `elicitationSupported: false`: вызов без `confirm` вернёт preview и `confirmToken`, который
     живёт 60 с. Сравни preview с планом поле за полем, затем повтори **идентичный** вызов с
     `"confirm":"<token>"`. Делай это только если человек уже подтвердил именно эти аргументы
     (`ПОДТВЕРЖДАЮ`, а для вывода ещё и `ВЫВОД`). Токен может погасить и сама модель, поэтому
     человеческое подтверждение здесь обязательно.
4. Ответ `CONFIRM_EXPIRED` означает, что ничего не отправлено. Повтори шаг 1. Если всё
   совпадает и план ещё действителен, возьми новый preview с теми же аргументами и погаси
   токен. Если что-то изменилось, нужно новое подтверждение.
5. После каждого шага сверься с историей (2.7) и запиши строку журнала.

### 2.6 Ответы: что точно не отправлено

| Ответ | Значит | Действие |
|---|---|---|
| `CONFIRM_INVALID`, `CONFIRM_EXPIRED`, `CONFIRM_MISMATCH` | токен отклонён до отправки | новый preview по 2.5.4 |
| `CONFIRM_DECLINED`, `CONFIRM_CANCELED` | человек отказался или закрыл форму | стоп, нужно новое согласие |
| `CONFIRM_UNAVAILABLE` | форма не открылась, ничего не отправлено | спроси человека, затем тот же подтверждённый вызов |
| `TIER_DISABLED`, `TRANSFER_VALUE_CAP`, `DAILY_VALUE_CAP`, `UNVALUABLE_TRANSFER`, `UNKNOWN_ACCOUNT`, `-32602` | отказ гейта или схемы до отправки | стоп, доложи |
| **всё остальное**: `UNKNOWN_OUTCOME`, `EXCHANGE_ERROR`, `INSUFFICIENT_FUNDS`, `AUTH_FAILED`, `BAD_REQUEST`, `INTERNAL_ERROR`, таймаут хоста, обрыв, нет ответа | запись могла уйти | сверка по 2.7, без повторов |

### 2.7 Сверка

- Пустой `get_safety_status.unresolvedIntents` **не доказывает**, что ничего не ушло. При
  `UNKNOWN_OUTCOME` журнал закрывает intent записью `error`, и он из списка пропадает. Таймаут
  хоста сервер вообще не видит. Список показывает только intents, оборванные падением процесса.
- Сравни снимок до вызова с живой историей. Нужна новая запись после снимка с той же суммой,
  адресом и сетью или с теми же кошельками, плюс изменение балансов. Нашлась — шаг исполнен,
  запиши её `id`. Не нашлась — исход по-прежнему неизвестен: доложи, подожди, прочитай ещё раз.
  Ничего не повторяй.
- A: `fetchWithdrawals` (`id`, `txid`, `status`, `fee`). B: `fetchDeposits` с тем же `txid`.
  Пока статус не `ok`, шаг 4 не делай. Если фактическое зачисление меньше суммы шага 4, остановись
  и запроси новое подтверждение.
- Внутренние переводы проверяй через `fetchTransfers` (у Gate и WhiteBIT его нет — только по
  балансам). Расхождение больше 0.01 USDT — доложи.

## Сценарий 3. funding ↔ trading/margin на одной бирже

Цикл тот же: режим аккаунта → доступная сумма и резерв → план из одного `transfer` →
`ПОДТВЕРЖДАЮ <PLAN-ID>` → перепроверка → вызов → сверка обоих кошельков. Имена кошельков бери
только из таблицы в [`references/exchanges.md`](references/exchanges.md). У Gate и Bitget
`funding` — это алиас `spot`, и перевод `funding → spot` там бессмысленен. У BingX `future` —
это `stdFutures`, а USDT-M perpetual — `swap` или `linear` (`USDTMPerp`).

## Сценарий 4. Hyperliquid — мониторинг маржи

Профиль содержит только публичный `walletAddress`, без ключей и без `funds`/`trading`. Поля
маржи есть **только** в `info`:

```text
call_read_method {"exchange":"hyperliquid","account":"hl-watch","method":"fetchBalance","includeInfo":true}
call_read_method {"exchange":"hyperliquid","account":"hl-watch","method":"fetchBalance","params":{"type":"spot"}}
get_positions {"account":"hl-watch"}
```

Из `info` сообщай `marginSummary.accountValue`, `totalMarginUsed`, `crossMaintenanceMarginUsed` и
`withdrawable`; `get_balance` их не показывает. Без профиля читай через
`call_read_method {"exchange":"hyperliquid","method":"fetchBalance","params":{"user":"0x…"},"includeInfo":true}`.

## Строка журнала в чате

```
[<UTC>] <PLAN-ID> шаг <n> <tool> <alias> → <ok|код> id=<…> txid=<…> D/W/C=<…>
```

## Когда остановиться и спросить

Нет нужного профиля или тира; `configProblems` или `unresolvedIntents` не пусты; режим
аккаунта, доступная сумма, флаг сети, минимум, контракт или валюта комиссии неизвестны; preview
или форма не совпадают с планом; не было явного `ПОДТВЕРЖДАЮ` или `ВЫВОД`; адреса нет в
whitelist A; исход записи неизвестен; Hyperliquid оказался источником или получателем USDT.
