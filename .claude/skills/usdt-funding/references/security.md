# Секреты, подключение к хостам, права ключей

Агент видит только алиасы и результаты инструментов. Ключи передаёт серверу оператор через
окружение запуска. В репозитории, конфигах хоста, argv и чате значений нет.

## Контракт окружения

- **Один MCP-сервер = один аккаунт.** У каждого сервера свой `config.json` с одним аккаунтом
  и уникальным алиасом. Уникальность нужна среди всех серверов, потому что журнал общий
  (см. [`ccxt-mcp.md`](ccxt-mcp.md)).
- ccxt-mcp берёт ключи из `<EXCHANGE>_APIKEY`, `<EXCHANGE>_SECRET`, а для OKX, Bitget и KuCoin
  ещё из `<EXCHANGE>_PASSWORD` (API passphrase). Для Gate id — `gate` (`GATE_*`). Hyperliquid
  переменных не получает.
- `loadEnvKeys` не включайте и `CCXT_MCP_APIKEY*` / `CCXT_MCP_EXCHANGE*` не задавайте: они
  создают аккаунт `default`. Два аккаунта одной биржи в одном процессе получат один и тот же
  ключ.

**Автоматической изоляции секретов между аккаунтами нет.** Claude Code передаёт каждому
MCP-серверу всё окружение, в котором запущен хост (проверено). Префиксные имена вроде
`OKX_MAIN_*` и подстановка `${…}` в `.mcp.json` ничего не изолируют: значения получат все
серверы, а заодно и shell агента. Codex передаёт серверу только имена из его `env_vars`
(проверено), но значения всё равно лежат в окружении хоста. Видит ли их shell агента, решают
настройки Codex, и здесь это не проверялось, поэтому считайте, что видит. Поддерживаются две
схемы.

### Схема A: один аккаунт с ключом на один запуск хоста

В окружении запуска есть ключи **только одного** аккаунта, а остальные серверы этого запуска
работают без ключей (например, Hyperliquid). Маршрут A → B — это два отдельных запуска: в
первом сверяются обе сети и выполняется вывод с A. Сохрани в чате результат вывода по 2.5
скилла. Во втором запуске по хешу из чата сверь депозит на B и выполни подтверждённый
внутренний перевод с ключом B. Агент в таком запуске технически
может прочитать этот ключ (тот же ОС-пользователь, правило 1 SKILL.md это запрещает), поэтому
ограничения на бирже обязательны.

Оператор загружает значения своим способом в свой shell, а хост запускает так, чтобы осталось
только разрешённое (bash):

```bash
( unset $(compgen -e | grep -vxE 'HOME|PATH|TERM|LANG|OKX_APIKEY|OKX_SECRET|OKX_PASSWORD'); exec claude )
```

Значения в argv не попадают. Проверено фиктивным сервером, который записывает только имена:
чужие `BYBIT_*` и прочие переменные до серверов не дошли. Если хосту для входа нужна своя
переменная, добавьте её имя в список.

### Схема B: отдельный запуск на каждый сервер (делает оператор)

В конфиге хоста `command` указывает на запускатель оператора вне репозитория, который агент не
может ни читать, ни менять (например, другой ОС-пользователь с фиксированным правилом запуска).
Запускатель стартует ccxt-mcp только с переменными своего аккаунта. В окружении хоста и в его
конфиге секретов нет. Как хранить секреты и чем запускать, решает оператор: навык это не
задаёт, и своего кода для этого в репозитории нет.

### `config.json` профиля (секретов нет, меняет только оператор)

```json
{
  "settings": { "strictPermissions": true, "hideDisabledTools": true },
  "accounts": {
    "okx-main": {
      "exchange": "okx",
      "funds": "live",
      "maxTransferValue": 200,
      "maxDailyValue": 500,
      "confirm": "always",
      "dryRun": true
    }
  }
}
```

Права на файл — `chmod 600`, владелец — пользователь сервера. С `strictPermissions: true` файл с
другими правами сервер отвергает, и `get_safety_status` показывает
`REFUSED (strictPermissions)` в `configProblems` (проверено). Профиль только для чтения — без
`funds` и `trading`. Hyperliquid:
`{"accounts":{"hl-watch":{"exchange":"hyperliquid","walletAddress":"0x…"}}}`. Начинайте с
`"dryRun": true` и снимайте его только после того, как план прогнан.

## Граница: тот же ОС-пользователь или отдельный

- **Тот же пользователь, что и shell агента** (схема A). Агент может прочитать окружение
  сервера (`/proc/<pid>/environ`; проверено, значения в `ps` не видны, а в `environ` видны), его
  файлы и журнал. Deny-правила хоста границей не являются. Такой режим подходит для профилей
  только для чтения или при жёстких ограничениях на стороне биржи.
- **Отдельный пользователь или контейнер на стороне оператора** (схема B). Shell агента не
  читает окружение и файлы сервера. Риск остаётся: если агент может сам запустить сервер, у
  его клиента нет нативной формы, сервер выдаст токен, и агент подтвердит запись сам.
- В обоих случаях ограничения на бирже обязательны (таблица ниже).

## Регистрация в хостах (без секретов)

Пути `<APP_DIR>` (каталог установки, см. [`ccxt-mcp.md`](ccxt-mcp.md)) и `<PROFILES>`
подставьте свои.

**Claude Code** — `.mcp.json` в проекте или `claude mcp add-json -s user <name> '<json>'`:

```json
{
  "mcpServers": {
    "ccxt-okx-main": {
      "command": "/usr/bin/node",
      "args": ["<APP_DIR>/node_modules/ccxt-mcp/js/server.js"],
      "env": { "CCXT_MCP_CONFIG": "<PROFILES>/okx-main/config.json" }
    }
  }
}
```

Ключи сервер берёт из окружения запуска (схема A) или из запускателя (схема B). Серверы из
`.mcp.json` проекта нужно один раз одобрить в интерактивном `claude`.

**Codex** — `~/.codex/config.toml` (или `$CODEX_HOME/config.toml`):

```toml
[mcp_servers.ccxt-okx-main]
command = "/usr/bin/node"
args = ["<APP_DIR>/node_modules/ccxt-mcp/js/server.js"]
env = { CCXT_MCP_CONFIG = "<PROFILES>/okx-main/config.json" }
env_vars = ["OKX_APIKEY", "OKX_SECRET", "OKX_PASSWORD"]
startup_timeout_sec = 30
tool_timeout_sec = 120
```

`env_vars` пробрасывает серверу только перечисленные имена (проверено). `${…}` внутри `env`
Codex **не** раскрывает. Второй аккаунт той же биржи требует отдельного запуска. Остальное
— как в схемах A и B.

Таймаут хоста не останавливает отправку на сервере (проверено). После него — только сверка,
см. SKILL.md, 2.7.

## Подключение навыка

- **Claude Code** находит `.claude/skills/usdt-funding/` в проекте. Для всех проектов
  скопируйте папку в `~/.claude/skills/`.
- **Codex** `.claude/skills` **не** читает (проверено). Сделайте в репозитории
  `mkdir -p .agents/skills && ln -s ../../.claude/skills/usdt-funding .agents/skills/usdt-funding`
  (симлинк проверен) или скопируйте папку в `~/.codex/skills/`.

## Smoke-check на каждом хосте (без модели и без ключей)

| Хост | Навык найден | Сервер подключён |
|---|---|---|
| Claude Code 2.1.331 | `claude --debug-file <log>` → в логе `Loaded … skills (… project: 1 …)` | `claude mcp list` → `ccxt-okx-main … ✔ Connected` |
| Codex 0.172.0 | `codex debug prompt-input \| grep -c usdt-funding` ≥ 1 | `codex mcp get ccxt-okx-main` (значения `env` замаскированы `*****`); `codex debug prompt-input` запускает сервер |

Затем в сессии попросите агента вызвать `get_safety_status` и `list_accounts`. Должно быть
`version: "0.1.3"`, `ccxtVersion: "4.5.84"`, пустой `configProblems`,
`elicitationSupported: true` (оба хоста объявляют `elicitation.form`, проверено по
`initialize`) и ожидаемые уникальные алиасы.

## Права ключей на бирже

| Профиль | Права | Обязательно |
|---|---|---|
| только чтение | чтение | IP allowlist |
| внутренний перевод | чтение + внутренний перевод | IP allowlist, без вывода |
| вывод (биржа A) | чтение + вывод (+ перевод) | IP allowlist, whitelist адресов (адрес B вносит человек с 2FA), лимит вывода на бирже |
| Hyperliquid | ключ не нужен | только публичный адрес |

Плюс `maxTransferValue` и `maxDailyValue` в профиле, `implicitWrites` выключен,
`confirm` ≠ `never`.

## Ротация

Плановая ротация, а при подозрении — немедленная. Удалите ключ в кабинете биржи, выпустите
новый с теми же минимальными правами и allowlist и обновите значение только для запуска этого
аккаунта. Если ключ попал в чат, лог или репозиторий, считайте его скомпрометированным:
отзовите и проверьте историю выводов и whitelist.
